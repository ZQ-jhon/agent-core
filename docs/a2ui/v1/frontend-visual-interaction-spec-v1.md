# A2UI 前端演示页视觉与交互规范 v1

状态：视觉评审稿，待泛前端开发专家确认实现映射

适用协议：A2UI Form Profile `1.0.0`

适用场景：单字段修改、条件化资料补全、必要约束申请/预约

设计目标：一个任务、一组最小必要字段、一次明确结果

## 1. 核心结论

A2UI 演示页不应呈现为“通用后台表单生成器”，而应呈现为 Agent 对话中的一张聚焦任务卡：用户先确认当前对象与任务，再填写不超过 7 个必要字段，最后获得明确结果。

v1 采用单列、低干扰、强状态识别的任务型表单。桌面端也不使用双列字段，以避免动态显隐后阅读顺序和键盘顺序分离。页面的唯一识别性设计是“任务锚点带”：在表单标题之前稳定呈现当前任务、目标对象和预期结果；它编码上下文，不作为装饰。

该方向同时解决三类问题：

- 业务表达：用户始终知道“正在处理什么”，不会把 Schema 演示误认为全量资料编辑页。
- 操作效率：短表单无需搜索字段，联动字段只在必要时出现。
- 实现一致性：Schema 决定内容与顺序，宿主设计系统统一决定视觉，不允许每个业务动作自定义样式。

## 2. 设计原理与审美逻辑

### 2.1 页面任务与目标用户

- 目标用户：在 Agent 对话中执行资料修改、资料补全、预约或申请的运营人员与业务用户。
- 页面唯一任务：让用户确认上下文并完成当前动作，不承载对象全量浏览、复杂流程编排或配置管理。
- 视觉气质：清晰、克制、可信，强调信息与状态，不使用营销渐变、大面积插画、玻璃拟态或装饰性动效。

### 2.2 任务锚点带

任务锚点带位于业务表单最上方，以 4 px 主色左边线、浅主色背景和三段文本表达：

1. 当前任务，例如“修改联系电话”；
2. 目标对象，例如“王某 · 客户编号 1024”；
3. 预计结果，例如“提交后立即更新”。

它是宿主层信息，不是新的 Schema 组件。宿主未获得对象或结果信息时，不得伪造内容，也不得用组件 ID、formId 或 requestId 代替用户可理解的上下文。数据契约未确认前，仅展示 Form 的 title/description。

### 2.3 单列是 v1 的明确选择

即使在桌面端，字段也保持单列。原因是：

- v1 强调最小字段集，双列不会显著缩短页面；
- 联动显隐在双列中容易造成空洞、跳位和阅读顺序变化；
- 单列可保证视觉顺序、DOM 顺序和键盘顺序一致；
- 中英文标签长度变化时无需重新计算跨列布局。

只有演示控制区可使用多列；业务表单字段不得根据屏幕宽度自动拼成双列。

## 3. 信息层级和页面结构

### 3.1 演示页分层

演示页分为两层，必须在视觉上明确隔离：

1. 演示控制层：Schema 示例选择、Mock/HTTP 数据源切换、重新加载；仅用于开发和验收。
2. 用户任务层：任务锚点、表单、反馈和业务操作；模拟真实嵌入 Agent 的体验。

演示控制层使用次级灰底、12–14 px 文本和“演示控制”标题，不得使用业务主按钮样式。窄屏可折叠，但其控件仍保持正常键盘可达。任何演示诊断信息不得插入业务表单的错误摘要。

### 3.2 用户任务层顺序

从上到下固定为：

1. 任务锚点带（宿主信息，可缺省）；
2. Form title；
3. Form description；
4. 静态 Alert/Markdown 内容；
5. 表单级错误摘要或通用反馈；
6. Section 与字段；
7. 操作区；
8. 提交成功或失败后的结果反馈。

错误摘要必须位于标题说明之后、第一个可编辑字段之前。动态成功/失败反馈不得与静态业务提示混用同一个视觉容器。

### 3.3 文案职责

- title 说明用户正在完成的任务，使用动作和对象，例如“补全客户资料”，不写“动态表单演示”。
- description 说明为什么需要这些信息、提交后发生什么，控制在 2 行内。
- label 只命名字段，不承担格式说明。
- helpText 解释用途、格式或条件原因，只做一件事。
- placeholder 仅提供输入示例，不重复 label，不作为必填提示。
- Button 使用结果导向动词，如“保存联系电话”“提交访问申请”；除协议演示外避免泛化的“提交”。
- 失败文案说明问题与下一步，不使用“发生未知错误”“请稍后再试”等无行动信息的表达。

### 4.3 字体层级

字体栈：`Inter`、`PingFang SC`、`Noto Sans SC`、`Segoe UI`、系统无衬线。宿主未提供 Inter 时直接使用系统字体，不临时加载第三方字体。

| 层级 | 字号/行高 | 字重 | 用途 |
| --- | --- | --- | --- |
| Form title | 24/32 px | 650 | 当前任务标题 |
| Section title | 16/24 px | 650 | 字段分组 |
| Body | 14/22 px | 400 | 描述、Markdown 正文 |
| Label | 14/20 px | 600 | 字段标签 |
| Input/Button | 14/20 px | 400/600 | 桌面控件 |
| Help/Error | 12/18 px | 400/500 | 辅助说明、字段错误 |
| Meta | 12/18 px | 500 | 演示控制、状态元信息 |

窄屏输入控件文字统一为 16/24 px，避免移动浏览器自动缩放。标题、label、按钮和错误文案允许换行；不得以省略号截断关键任务或错误信息。

### 4.4 圆角、边框和阴影

- 表单卡片：16 px 圆角；桌面阴影 `0 12px 32px rgba(23,32,51,0.08)`。
- 输入、按钮、Alert、任务锚点：10 px 圆角。
- 控件：1 px 边框；聚焦使用 2 px Focus 边框加 3 px、30% 透明度外环，不通过阴影模糊替代清晰轮廓。
- 分隔线只用于演示控制层和操作区，颜色为 Divider；Section 之间优先使用留白，不堆叠卡片。
- 窄屏取消卡片阴影与外层圆角，使页面保持完整可用宽度。

### 4.5 控件尺寸

- 单行输入、Select、DatePicker、Button：桌面最小高 44 px，窄屏 48 px。
- TextArea：初始最小高 112 px，按 rows/maxRows 增长；允许纵向调整，不允许横向拖拽破坏布局。
- Radio、Checkbox、Switch 的整行点击区域最小高 44 px；图形控件不小于 20×20 px。
- 图标按钮（如清除、移除文件）可见图形不小于 16 px，命中区不小于 44×44 px，并提供可感知名称。

## 5. 通用组件状态

| 状态 | 视觉 | 行为与验收 |
| --- | --- | --- |
| 默认 | 1 px Border default；白底 | label、值和说明均可读 |
| Hover | Border hover；不改变布局 | 仅有精确指针的设备启用，不作为唯一反馈 |
| Focus-visible | Focus 边框与外环 | 只在键盘/等价输入出现；任何状态下轮廓不被裁切 |
| Filled | 与默认边框一致，值用 Text primary | 不用常驻主色边框表示“已填写” |
| Invalid | Error border；下方 Error 文字 | 同时设置 `aria-invalid` 与 `aria-errormessage` |
| Disabled | Disabled surface、Disabled text、默认光标 | 使用原生 disabled；不响应 hover/focus，不执行客户端校验 |
| Read-only | Surface 白底、虚线或弱灰边框 | 可聚焦、可复制；明确显示“只读”，值参与提交 |
| Loading | 内容位置稳定，显示文字与进度 | 不能只显示旋转图形；状态对辅助技术可感知 |

错误边框优先级高于 Hover，Focus 外环优先级高于错误边框；错误字段聚焦时同时保留 Error border 和 Focus 外环。

## 6. 校验、错误与焦点

### 6.1 必填表达

label 后使用可见文字“必填”，12/18 px、Error 色；同时设置 `aria-required="true"`。不得只显示红色星号。可选字段默认不逐项标“选填”，只有可能造成误解时才显示。

### 6.2 校验时机

- change：更新值与联动，不立即展示新的格式错误。
- blur：校验当前字段；用户尚未触碰的字段不提前报错。
- submit：校验所有可见且启用字段，失败则阻止 action。
- server response：服务端错误覆盖同一路径的旧服务端错误；用户修改该字段后清除该路径的服务端错误，但不清除其他字段错误。

每个字段默认只显示首个错误。字段下方顺序为：错误 → 仍有助于修正的 helpText。若 helpText 与错误重复，可在错误期间隐藏 helpText，避免双重说明。

### 6.3 错误摘要

提交失败后：

1. 在 Form 顶部插入错误摘要；
2. 摘要标题为“请检查以下内容”，显示错误数量；
3. 每个字段列出首个错误，并以链接指向字段；无法映射的服务端错误仍列入摘要；
4. 将程序焦点移到摘要容器，容器可用 `tabindex="-1"`；
5. 用户激活错误链接后，将焦点移到对应字段；折叠 Section 必须先展开；
6. 不自动滚动到页面底部，也不清空任何已填值。

这里采用“先聚焦摘要、再由链接定位字段”，以满足协议组件目录的错误上下文要求。视觉滚动需尊重 `scroll-margin-top: 24px` 等价距离，字段聚焦后其 label 与错误文字必须同时在视口内。

## 7. 联动字段交互

- 新字段出现使用 160 ms ease-out 的高度与透明度过渡；消失使用 120 ms ease-in。不得使用位移超过 8 px、弹簧或连续动画。
- `prefers-reduced-motion: reduce` 时取消过渡并立即更新。
- 触发联动的源控件保持焦点；不得自动把焦点抢到新字段。
- 新增字段在首次出现时显示一行原因说明，例如“因选择‘企业’而需要填写”。原因可由业务文案提供；前端不得从规则表达式自动拼接用户文案。
- 隐藏节点不占空间、不可聚焦、从辅助技术树移除并停止客户端校验。
- 当前聚焦字段若因外部规则被隐藏，焦点回到触发该规则的源控件，并礼貌播报状态变化。
- 同一批联动只进行一次整体布局更新，避免多个字段依次跳动。

## 8. 操作区、提交与结果

### 8.1 操作区

- 同一 Form 最多一个 primary submit。
- 主操作位于操作区末端；secondary/reset 位于其前，danger 与普通 submit 分组并保持至少 16 px 间距。
- 操作区使用正常文档流，不做悬浮底栏。v1 最多 7 个可编辑字段，固定底栏会遮挡内容且收益有限。
- 窄屏按钮纵向排列、宽度 100%，DOM 顺序与视觉顺序一致，不使用 CSS 倒序。
- 取消并返回对话属于宿主动作，当前 Schema action 未定义 cancel；未确认宿主契约前不得伪装成 reset。

### 8.2 提交中

- submit Button 保持原宽度，label 切换为 loadingLabel 或“处理中…”，显示进度状态并设置 `aria-busy`。
- 防止重复触发，但不能让焦点从按钮消失；不得简单替换成不可聚焦的新节点。
- 表单值保持可见，提交期间阻止修改和其他 action；使用事件守卫和可感知忙碌状态，不依赖移除整个表单 DOM。
- 超过 1 秒显示可见处理中状态；超过业务超时后按失败规则解锁，不提供无依据的进度百分比。

### 8.3 成功

- 在原表单位置显示 Success 结果区，标题与按钮动作使用同一动词，例如“联系电话已保存”。
- 只显示任务必要结果；敏感值按业务规则脱敏。
- 结果区获得礼貌播报，不强制把焦点移出用户当前位置；若表单整体被替换，焦点移到结果标题。
- “返回对话/继续”是宿主层动作；在契约未确认时，演示页只展示结果，不伪造下一步。

### 8.4 失败与重试

- 字段错误按第 6 节处理。
- 通用或网络失败在表单顶部显示 Error Alert，保留所有值，解除忙碌锁，并提供明确重试入口。
- 只有后端标识可重试或宿主确认请求安全时才显示“重试”；否则显示“返回对话”。
- revision 冲突使用 Warning/Error 结果：“表单内容已更新，请重新加载后继续”；禁止继续提交旧表单。
- 重试沿用当前输入和同一任务上下文；不得悄悄恢复初始值。

### 8.5 确认对话框

- 最大宽度 480 px，内边距 24 px，标题 18/26 px，正文 14/22 px。
- 打开时焦点进入弹窗，关闭时回到触发按钮；Tab 焦点被限制在弹窗内，Esc 等价于取消。
- 涉及不可逆或高风险动作时默认焦点放在取消按钮；确认按钮使用动作名称，不写“确定”。
- 窄屏可使用底部对话面板，但必须保留相同语义、焦点管理和按钮顺序。

## 9. 页面级状态规范

| 状态 | 呈现 | 行为/验收 |
| --- | --- | --- |
| Form loading | 标题骨架 + 3 个字段骨架；不模拟真实敏感值 | 容器 `aria-busy`；加载完成后不自动抢焦点 |
| 空态 | “当前没有需要填写的内容” + 返回对话 | 不显示空白卡片或禁用提交按钮 |
| 协议/版本致命错误 | 独立 Error 状态，说明客户端无法打开该表单 | 不渲染部分业务表单，不执行 action/dataSource |
| 局部组件失败 | 等高占位 + 用户可行动说明 | 显示可报告的短标识；内部堆栈只进日志 |
| 远程选项加载 | Select 内可见“正在加载选项…” | 保留控件高度，旧请求不得覆盖新请求 |
| 远程选项空结果 | “没有匹配选项” | 不伪装成加载失败 |
| 远程选项失败 | 组件级 Error + “重试加载” | 不伪装为空结果；依赖值不可用时禁止提交 |
| 提交成功 | Success 结果区 | 显示任务结果与宿主下一步 |
| 提交失败 | Error Alert/错误摘要 | 保留值、解除锁、按安全语义提供重试 |

Loading 骨架使用中性灰，不使用主色脉冲；动画周期不短于 1.2 秒，Reduced Motion 下静止。

## 10. Schema v1 组件适配与验收清单

### 10.1 容器与内容

| 组件 | 视觉与交互要求 | 前端验收点 |
| --- | --- | --- |
| Form | 单列 720 px 内；title/description 后承载错误摘要与提交状态 | 原生 form 语义；title 提供可感知名称；Enter 提交仅在 `submitOnEnter` 条件满足时生效 |
| Section | 以 32–40 px 留白分组，标题 16/24；不为每组套卡片 | 优先 fieldset/legend；折叠按钮暴露 expanded/controls；错误链接可展开并定位 |
| Alert | 10 px 圆角、语义浅底、左侧结构标识；title 可选但 error/success 动态反馈必须有明确标题 | info/success/warning/error 均有文字语义；动态状态使用合适 live region；静态提示不重复播报 |
| Markdown | 正文 14/22；标题最多三级视觉层级；段落间 12 px、列表项 6 px；链接为 Primary 色并有下划线 | 不渲染原始 HTML/图片/iframe；键盘焦点清晰；超长 URL 换行，不造成横向滚动 |

### 10.2 输入组件

| 组件 | 视觉与交互要求 | 前端验收点 |
| --- | --- | --- |
| TextInput | 44/48 px 高；label、control、help/error 固定顺序 | placeholder 不替代 label；autocomplete/inputMode 白名单；readOnly 可聚焦复制且与 disabled 可辨 |
| TextArea | 最小高 112 px；只纵向增长；剩余字数放右下方但不覆盖输入 | rows/maxRows 生效；换行保留；字符计数非打断播报；长文本不撑破容器 |
| NumberInput | 单位位于控件内尾部或紧邻右侧，采用 Text secondary | 允许负号/小数点中间态；blur/submit 再提示；提交前归一化为 number/null；单位不进入值 |
| Select | 与输入同高；下拉面板最大高 320 px；选项最小高 40 px | 静态优先原生 select；自定义 combobox 完整支持方向键、Enter、Esc；有 loading/empty/error；clearable 可达 |
| RadioGroup | 默认纵向，项间 8 px；横向模式可换行，窄屏超过 3 项强制纵向 | 组 label/错误与容器关联；方向键语义正确；整行命中区 ≥44 px；disabled option 可辨 |
| CheckboxGroup | 默认纵向；选中框与多行 label 顶部对齐 | 每项独立 label；组级错误与组容器关联；数组无重复值；窄屏不压缩为难点按多列 |
| DatePicker | 与输入同高；日期图标不作为唯一触发区 | 允许键盘输入和日期面板操作；显示本地化、提交 ISO；min/max 禁用状态同时提供说明 |
| Switch | label 描述设置本身，状态文字显示 onLabel/offLabel；图形 36×20 px 以上 | 暴露 checked；Space 切换；整行命中区 ≥44 px；on/off 不只靠颜色 |
| Upload | 虚线选择区只作为增强，必须有明确 Button；文件项显示名称、大小、状态与操作 | 键盘选择；进度可感知；成功才写值；失败提供重试/移除；超限、类型、服务端失败文案可区分 |

### 10.3 操作组件

| 组件 | 视觉与交互要求 | 前端验收点 |
| --- | --- | --- |
| Button | primary 实底、secondary 白底、danger 红色、text 无容器；高度 44/48 px | hover/focus/pressed/disabled/loading 完整；使用原生 button；请求中防重复且焦点不消失；同一 Form 最多一个 primary submit |

### 10.4 Upload 文件项状态

每个文件项最少覆盖：等待上传、上传中、已上传、上传失败、移除中。上传中显示文件名、可感知进度和取消/移除策略；失败显示原因分类与重试，不把失败文件写入 `UploadValue[]`。服务端未返回安全文件引用时不得显示“已上传”。

## 11. 响应式与国际化规则

### 11.1 响应式

- 业务表单始终单列，不产生横向滚动。
- <768 px 时页面与卡片同宽，移除阴影和圆角，输入字号 16 px。
- <480 px 时操作按钮和确认对话框按钮纵向排列；不得通过视觉倒序改变键盘顺序。
- Radio/Checkbox 横向布局在标签换行、选项超过 3 个或宽度不足时自动转纵向。
- 下拉面板、日期面板和确认对话框不得超出可视区；软键盘出现时当前字段及错误仍可滚动到可见位置。
- 在 320 CSS px 宽度和 200% 文本缩放下，无双向滚动、内容遮挡或不可达操作。

### 11.2 国际化

- 所有标签、按钮、提示和错误允许增长至中文长度的约 2 倍，不设固定文本宽度。
- 按钮设置最小尺寸而非固定宽度；桌面可扩展，窄屏全宽。
- 日期显示跟随 locale，数据值仍为 `YYYY-MM-DD`；数字与单位之间遵循 locale 间距。
- 不把图标方向、颜色或文字长度作为业务语义；未来 RTL 接入时，任务锚点边线、尾部图标和操作顺序需逻辑化处理。
- 生产 UI 不显示未本地化的错误码；诊断码仅作为次级信息，并与 requestId 一样避免暴露敏感内容。

## 12. 可访问性验收

P0 验收必须包含：

1. 仅用键盘完成加载、填写、联动、校验、确认和提交；Tab 顺序与 Schema 树顺序一致。
2. 所有可交互项存在清晰 `:focus-visible`，轮廓不被 overflow 裁切。
3. label、help、error 使用稳定 ID 关联；required、invalid、busy、expanded、checked 状态可感知。
4. 提交失败先聚焦错误摘要；摘要链接能展开 Section 并聚焦字段。
5. 动态字段出现/隐藏、上传进度和结果变化使用适度 live region，不重复播报静态内容。
6. 颜色不是任何状态的唯一表达；正文对比度 ≥4.5:1，焦点和控件边界 ≥3:1。
7. Reduced Motion 下取消非必要动效；Loading 仍有文字或静态状态。
8. 320 px 宽度、200% 文本缩放和高对比模式下可完成关键路径。

## 13. QA 可直接执行的视觉验收

### P0：开发前必须冻结

- [ ] 演示控制层与业务表单层视觉隔离，不把 Mock/HTTP 信息当作业务内容。
- [ ] 业务表单为单列，最大宽 720 px；桌面、平板、窄屏间距符合第 4 节。
- [ ] 14 个 Schema v1 组件均覆盖默认、禁用、聚焦和错误相关状态；可交互组件额外覆盖 hover/pressed/loading（适用时）。
- [ ] 必填使用可见文字与 `aria-required`，不只用星号或颜色。
- [ ] blur/submit/server error 时机与第 6 节一致；提交失败聚焦错误摘要。
- [ ] 联动字段不抢焦点，隐藏后不占位、不校验、不可达；Reduced Motion 生效。
- [ ] submit 防重复且焦点不消失；成功/失败保留正确上下文和值。
- [ ] Loading、空态、致命协议错误、局部组件失败、远程选项三态、成功与失败均可单独演示。
- [ ] 320 px、200% 缩放、键盘路径和对比度通过人工验收。

### P1：系统优化

- [ ] 统一埋点可区分加载、首次错误、修正、重试与成功，不采集原始敏感值。

### P2：长期沉淀

- [ ] 建立组件状态截图基线与自动化可访问性回归，但不能替代键盘与读屏人工测试。

## 14. 实现映射、未决项与评审结论

### 14.1 可直接实现的冻结项

- 单列 720 px 表单、响应式间距、字体与色彩 Token；
- 全组件状态、错误摘要、联动过渡、焦点策略；
- 页面 loading/empty/fatal/success/failure 与远程选项状态；
- 14 个协议组件的视觉和可访问性验收点；
- 演示控制层与业务层隔离。

### 14.2 禁止前端自行决定的未决项

| 未决项 | 原因 | 临时边界 |
| --- | --- | --- |
| 任务对象摘要、数据用途、预计结果的宿主数据契约 | Form 仅有 title/description，Schema 无专用上下文组件 | 无数据时不伪造任务锚点内容；不得新增私有 Schema prop |
| 取消/返回对话 action | v1 action 仅 submit/reset/upload | 不得把 reset 当取消；等待宿主动作契约 |
| 首批业务动作与成功文案 | 产品评审尚未确认实际业务动作 | 使用协议通用 fixture 验收，不宣称业务上线 |
| Upload/Markdown 是否进入首批三场景 | PRD 将附件/富文本排除首批，协议 v1 仍包含组件 | 组件必须实现和验收；首批场景是否启用由产品确认 |
| 隐藏/禁用字段的提交载荷 | PRD 表述“不提交”，协议强调完整 data 并由规则清值/服务端裁决 | 视觉上隐藏且停止客户端校验；payload 不由前端猜测，需产品/协议给唯一结论 |
| 高风险动作的二次确认条件与默认焦点 | 依赖具体业务风险等级 | 仅按 Schema confirm 渲染，不自行推断风险动作 |

### 14.3 视觉评审结论

本规范对信息层级、视觉 Token、交互状态、14 个组件、响应式和可访问性给出可实现、可验收的基线。设计方向可进入泛前端可实现性复审。

复审前置条件：泛前端开发专家需确认任务锚点宿主映射、提交中焦点保持、错误摘要定位、自定义 Select 键盘模型、联动批量过渡和 Upload 状态模型均可按本规范实现。第 14.2 节未决项不得由前端自行补充协议或业务语义；如阻塞首批演示，应回到产品/协议负责人确认。
